# Процесс разработки

Правила командной работы в репозитории. Основаны на [Definition of Done](DEFINITION_OF_DONE.md).

## Ветки

- `main` — стабильная ветка, напрямую в неё не коммитим.
- `feature/<кратко>` — новая функциональность (например, `feature/iteration-1`).
- `fix/<кратко>` — исправление дефекта.
- `docs/<кратко>` — только документация.

## Цикл работы над задачей

1. Взять Issue из текущего Milestone, назначить себя исполнителем (Assignee).
2. Создать ветку от актуального `main`.
3. Делать небольшие коммиты с понятными сообщениями на английском, в сообщении указывать номер Issue (`Closes #8` для последнего коммита задачи).
4. Отправить ветку и открыть Pull Request по шаблону, указать `Closes #N`, назначить рецензента (Reviewer).
5. **Code review.** Рецензент (не автор) проверяет изменения по чек-листу в шаблоне PR, оставляет замечания к строкам и либо одобряет (Approve), либо просит правки (Request changes).
6. Автор исправляет замечания новыми коммитами в ту же ветку.
7. После одобрения PR сливается в `main` кнопкой **Merge pull request**. Связанные Issues закрываются автоматически.
8. Проверить, что Issue закрыта, критерии приёмки отмечены, ветка удалена.

## Milestones (контрольные точки)

| Milestone | Срок | Состав |
|-----------|------|--------|
| Итерация 1 | 20.11.2026 | US-01, US-02, US-03, TECH-02, FR-01…FR-04 |
| Итерация 2 | 04.12.2026 | TECH-01, TECH-03, US-04, FR-05; приёмка MVP |
| Итерация 3 | 18.12.2026 | NFR-01, US-05, US-06 (версия 2) |

Каждый Issue привязан к своему Milestone. В конце итерации в Milestone остаются только невыполненные задачи; их переносят в следующую итерацию с записью в отчёте.

## Отчёт об итерации

По окончании итерации в docs/ добавляется отчёт по образцу [SPRINT_1_REPORT.md](SPRINT_1_REPORT.md): план, выполнение, результаты, отклонения.

## Защита ветки main (рекомендуется)

Settings → Branches → Add branch ruleset для `main`: требовать Pull Request и минимум одно одобрение. Тогда слияние без review невозможно (см. риск R6 в паспорте проекта).
