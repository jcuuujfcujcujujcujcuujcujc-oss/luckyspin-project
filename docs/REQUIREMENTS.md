# Спецификация требований

Роли: **Игрок**, **Оператор**. Приоритеты по MoSCoW. Числовые пороги учебные и подлежат согласованию.
Столбец «Версия» показывает, входит ли требование в MVP. Состояние реализации смотрите в Issues и Milestones, здесь оно не дублируется.

## Правила API: когда создаётся игрок

В MVP регистрации нет, поэтому правило создания игрока определено для каждого метода отдельно.

| Метод | Игрок не существует | Игрок существует |
|-------|---------------------|------------------|
| GET /api/slots/balance/{userId} (FR-01) | **Создаётся** со стартовым балансом 1000, ответ 200 | Возвращается текущий баланс, дубликат не создаётся |
| POST /api/slots/spin (FR-02, FR-04) | **Не создаётся**, ответ 404 и сообщение | Ставка обрабатывается по правилам FR-02…FR-04 |

Игрок создаётся только запросом баланса. Страница игры вызывает его при загрузке, поэтому в обычной работе `spin` всегда видит существующего игрока. Противоречия между FR-01 и FR-04 нет.

## Различие требований и решений

В список не включены технические решения. Например, «использовать Entity Framework Core InMemory» относится к реализации и описано в README, а требование NFR-03 описывает поведение системы.

## Проверка качества

- Слова «быстро» и «удобно» заменены измеримыми порогами (NFR-02, NFR-04)
- Дубли и конфликты устранены: FR-02 описывает ставку, FR-03 выплату, FR-04 ошибки ввода; правила создания игрока заданы таблицей выше
- Требования атомарны: у каждого одна проверяемая цель
